# Порядок работы команды meandme

МаксименкоАВ, GitHub — `almv9`. Работа ведётся по правилам ниже с соблюдением ограничений доступа и требований преподавателя.

## Задачи и ветки

Работа ведётся через GitHub Issues и pull request. Прямой push и force push в `main` запрещены.

1. До начала работы создаём issue: проблема, ожидаемый результат и критерии готовности.
2. Указываем исполнителя; для текущего состава это `almv9`.
3. Создаём отдельную ветку от актуального `main` под одну issue или связанный набор задач.
4. Реализуем изменение и открываем PR в `main` командного репозитория.
5. Исправляем замечания в той же ветке. После слияния закрываем связанные issues.

Названия веток — латиницей, без пробелов:

| Префикс | Назначение | Пример |
|---|---|---|
| `docs/` | Постановка и документация | `docs/p1` |
| `feature/` | Новая функция | `feature/12-find-duplicates` |
| `fix/` | Исправление ошибки | `fix/18-invalid-image` |
| `test/` | Тесты | `test/21-job-transitions` |
| `chore/` | Настройки и инфраструктура | `chore/25-ci` |

Числа в примерах заменяются реальными номерами issues. Ветку регистрации команды и ветку заявки в fork `Zadania` не используем для разработки сервиса. Один PR не должен объединять несвязанные изменения.

## Коммиты

Формат: `type: Описание выполненного изменения`.

- Тип пишется на английском: `docs`, `feat`, `fix`, `test`, `chore` или `refactor`.
- После двоеточия ставится пробел.
- Суть изменения описывается только по-русски, с большой буквы, в прошедшем времени: «Добавлена», «Исправлена», «Обновлены».

Примеры:

```text
docs: Описаны сценарии анализа фотогалереи
feat: Добавлена проверка переходов задания
fix: Исправлена обработка повреждённого изображения
test: Добавлена проверка повторного запроса с тем же ключом
chore: Настроен запуск тестов
refactor: Упрощён выбор исполнителя
```

Коммит должен описывать законченное понятное изменение. Не используем сообщения вроде `123`, `норм` или `final-final`. Не добавляем токены, пароли, локальные настройки и личные фотографии.

## Pull request

Перед открытием PR автор читает весь diff и проверяет отсутствие случайных файлов. Заголовок описывает результат изменения. В описании указываются:

- какую задачу решает изменение;
- что изменилось в поведении или документах;
- связанные issues;
- как проверено и что пока не проверено;
- известные ограничения и вопросы к проверяющему.

Если PR полностью закрывает issue, используем `Closes #N` с настоящим номером. Если выполнена только часть, пишем `Refs #N`, чтобы не закрыть задачу преждевременно. В PR практики 1 объединяем README, требования и правила работы в ветке `docs/p1`; незавершённые задачи реализации при этом не закрываются.

## Review и слияние

На практике 1 действует согласованный с преподавателем порядок для команды из одного человека: личный вклад подтверждается собственным влитым PR. Автор проверяет diff перед слиянием.

С практики 3 каждый участник делает содержательное review PR другой команды по распределению курса в `tasks/review_pN.md`. Наши PR проверяет назначенная команда. Внешние проверяющие оставляют комментарии, в том числе к строкам кода; назначение в Reviewers не требуется. Если состав meandme расширяется, автор назначает рецензента из своей команды в Reviewers и сливает PR после его review.

Проверяющий обращает внимание на:

- соответствие issue, требованиям и границам проекта;
- понятность сценариев, критериев приёмки и причин ошибок;
- корректность переходов Job и контрактов;
- тесты, последствия изменения и отсутствие лишней сложности.

Review содержит вопросы, замечания или объяснение проверенного поведения. Формальные сообщения без содержания не считаются полезным review. Существенные замечания исправляются либо обсуждаются с обоснованием решения.

Самопроверка не считается review чужого PR или независимым approval. По [правилам курса](https://github.com/AIProgramIngeneering2026/Zadania/blob/main/ПРАВИЛА.md) обязательное нажатие Approve не требуется; решение о слиянии принимает команда-владелец репозитория. Действующие ограничения ветки сохраняются.

После выполнения Definition of Done PR сливается доступным способом, разрешённым правилами командного репозитория. Само открытие PR ещё не означает, что работа принята. Для отчёта практики 1 сохраняем полную ссылку на фактически влитый PR; если выполнено review чужого PR, сохраняем и ссылку на него.

На практике 2 личные баллы считаются по участию в занятии: мини-тест и свой issue/комментарий `[poker]` во время пары. Для пропустивших свой влитый PR или содержательное review даёт половину личного балла. В отчёте приводятся фактические ссылки на вклад; PR практики 1 повторно не используется. Основание — [задание p2](https://github.com/AIProgramIngeneering2026/Zadania/blob/main/tasks/p2.md).

## Проверка изменений

Для документации проверяем пути, ссылки, единообразие терминов и соответствие README, требований и заявки. Не называем запланированные функции реализованными и не придумываем результаты тестов.

Для контрактов дополнительно выполняем `python tools/check_contract.py` в окружении с `requirements-contract.txt`; инструкция — в README. Проверяем все десять карт, ссылки на ADR и соответствие схем описанным ответам.

Для кода запускаем относящиеся к изменению проверки. После появления тестового окружения основная команда — `pytest`, она же запускается в CI. Изменения правил Job, анализаторов и обработки ошибок сопровождаются тестами этих правил. Обязательные тесты используют фиксированные файлы и fake-источник; доступность Picsum не должна определять результат CI. Проверка живой интеграции выполняется отдельно и описывается в PR.

К практике 7 инструкция `docker compose up --build` должна быть проверена из чистого клона с применением миграций. Пока соответствующие файлы и проверки не созданы, не указываем, что запуск уже работает.

## Definition of Done

Задача считается сделанной, когда выполнены применимые пункты:

- Критерии приёмки issue выполнены; способ проверки результата указан в PR.
- Изменение находится в PR, автор проверил diff.
- Документация и контракты обновлены, если изменилось поведение.
- Для изменений кода необходимые тесты добавлены или обновлены и проходят; настроенный CI зелёный. Для чисто документального PR без CI указана ручная проверка документации.
- Нет необсуждённых блокирующих замечаний; выполнены требования review и защиты ветки, применимые к этому PR.
- Секреты, личные данные и случайные файлы не добавлены.
- Известные ограничения отражены в PR и документации.
- PR влит в `main` командного репозитория; issue закрыта только при выполнении всей её задачи.

Для документальной задачи практики 1 результат — согласованные документы, а не реализованный сервис. Созданная issue с планом реализации не означает, что описанная функция уже готова.

## Использование ИИ

ИИ используется для подготовки текстов, объяснений, поиска отказных сценариев и проверки полноты документов. Автор самостоятельно проверяет результат и объясняет принятые решения.

В `docs/requirements.md` сохраняются промпт поиска дополнительных отказов, три предложения и принятые решения с обоснованием. Для практики 2 промпт и три находки по контрактам записываются в `docs/contract-check.md`. В описании PR указываем, для чего использовали ИИ. Не придумываем выполненные действия, ссылки на PR, личный вклад, review или результаты проверок.
