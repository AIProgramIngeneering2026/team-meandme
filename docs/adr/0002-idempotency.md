# ADR-0002. Создание Job по постоянному ключу идемпотентности

- Дата: 10 ноября 2026 года.
- Статус: принято.

## Контекст и ограничения

Клиент может дважды нажать кнопку или потерять ответ после сохранения Job. Два запроса могут прийти одновременно. Совпадение параметров само по себе не означает повтор: пользователь вправе запустить одинаковый анализ ещё раз.

## Решение

`POST /jobs` требует `Idempotency-Key`: 1–128 символов из `A–Z`, `a–z`, `0–9`, `_`, `-`. Ключ чувствителен к регистру, общий для экземпляра, хранится до конца жизни Job без срока истечения. Клиент использует новый случайный ключ для новой работы и сохраняет его до получения ответа.

Сначала проверяются формат JSON, поля и формат ключа, затем выполняется поиск ключа. Сравнивается пара строк `(dataset_id, operation)` без изменения регистра и пробелов; порядок полей JSON не влияет. Для существующего ключа одинаковая пара даёт 200 с тем же ID и текущим состоянием, другая — 409 `idempotency_conflict`. Новые проверки каталога и доступности Tool к старому Job не применяются. Поэтому повтор после изменения каталога возвращает прежний снимок, а не создаёт новое задание.

Для нового ключа проверяются операция, каталог и лимит очереди. Сохранение ключа, Job и снимка набора — одна транзакция. Ограничение уникальности ключа в БД обязательно. При гонке проигравший запрос перечитывает запись после фиксации победителя и возвращает 200 либо 409. На SQLite используется короткая транзакция записи; на PostgreSQL — ограничение уникальности и сериализация участка приёма новой работы. Сетевых вызовов внутри этой транзакции нет.

При неясном результате фиксации из-за сбоя соединения ответ — 503 `storage_unavailable`. Клиент повторяет тот же запрос с тем же ключом. Если транзакция была сохранена, получает 200; если откатилась, после восстановления создаётся один Job с ответом 202. Гарантия относится к созданию Job, а не к неизменности ответов внешнего Picsum.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Создавать Job при каждом POST | Повтор и потерянный ответ приводят к лишней работе |
| Считать ключом хеш параметров | Нельзя намеренно повторить такой же анализ |
| Хранить ключи только в памяти | Перезапуск разрушает защиту от дублей |
| Удалять ключи через час | Поздний повтор неожиданно запускает работу заново; для учебного объёма выигрыш мал |

## Цена решения

Таблица ключей растёт вместе с Job. Общие ключи не обеспечивают изоляцию пользователей; один клиент способен занять чужой выбранный ключ. Для учебного экземпляра используются случайные ключи и только общедоступные демонстрационные данные. Повтор создания после `failed` или `cancelled` возвращает прежний Job. Для новой попытки клиент отправляет новый ключ.

## Условия пересмотра

При появлении аккаунтов ключ связывается с владельцем. При введении удаления или срока хранения отдельно фиксируются срок защиты от дублей, ответ на просроченный ключ и поведение позднего повтора. Изменение сравниваемых параметров требует новой версии контракта.
