# ADR-0001. Один процесс и фоновое выполнение Job

- Дата: 10 ноября 2026 года.
- Статус: принято в проекте; реализация следует после практики 2.

## Контекст и ограничения

Набор содержит до десяти небольших изображений, анализ запускается одной командой разработки из одного человека. HTTP-ответ не должен ждать загрузки и вычислений. Для заданий выбраны жизненный цикл и хранение в БД. Требуется определить поведение после перезапуска.

## Решение

API и один Runner работают в одном процессе. Создание Job сохраняет `created` в БД и возвращает 202. Runner последовательно обрабатывает записи очереди; блокирующие вычисления выполняются в отдельном рабочем потоке, без блокировки HTTP. Не более двадцати Job находятся одновременно в `created`/`running`; новый запрос сверх лимита получает 503 `service_busy`, повтор существующего ключа читается штатно.

При старте, до обработки запросов, все старые `running` атомарно переводятся в `failed` с `execution_interrupted`. Задания в `created` остаются в очереди, а конечные состояния, включая `cancelled`, сохраняются. После восстановления клиент создаёт новый Job с новым ключом, если хочет повторить прерванный анализ. Полный результат записывается вместе с `done` в одной транзакции. Захват ожидающего Job согласован с операцией отмены. [ADR-0004](0004-cancel-created.md)

Если результат нельзя сохранить из-за БД, Runner останавливает получение новой работы; `/health` сообщает неготовность. После восстановления требуется перезапуск приложения. Запуск нескольких процессов или копий приложения с одной БД для этой версии не поддерживается: процедура старта иначе могла бы ошибочно завершить чужую работу.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Выполнить анализ внутри POST до ответа | Долгое ожидание связывает сетевой запрос клиента с обработкой; теряется смысл опроса Job |
| Отдельный worker и Redis/RabbitMQ | Добавляет инфраструктуру, подтверждения доставки и повторное выполнение при небольшом объёме |
| Только очередь в памяти | Теряет ещё не начатую работу после перезапуска |
| Продолжать старый `running` с середины | Требует контрольных точек и правил повторного получения изменяемых внешних файлов |

## Цена решения

Пропускная способность ограничена одним анализом. Сбой процесса прерывает текущий Job, и пользователь запускает новый вручную. Нужны сохранённая очередь и проверка состояния при старте. Нельзя масштабировать экземпляры без пересмотра протокола владения Job. Это уточняет p1, где обработка последствий аварии была исключена: теперь состояние после аварии определено, но возобновления расчёта нет.

## Условия пересмотра

Пересматриваем решение, если нужны несколько экземпляров, параллельные анализы, гарантированное продолжение длительной работы или ожидание очереди мешает демонстрации. Тогда вводим отдельного worker, владение заданием и правила повторного выполнения, а не просто увеличиваем число Uvicorn workers.
