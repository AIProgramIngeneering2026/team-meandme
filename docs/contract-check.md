# Проверка контракта колодой

Проверка выполнена при подготовке документов 10 ноября 2026 года для сервиса meandme. Это разбор проектного контракта, а не протокол вызовов работающего API. Колода — [К1–К10 из задания](https://github.com/AIProgramIngeneering2026/Zadania/blob/main/tasks/p2_poker/README.md#колода).

## К1–К10

| Карта | Конкретная ситуация и ответ контракта | Где закреплено |
|---|---|---|
| К1 Двойной клик | Два POST с ключом `demo-click-1`, набором `demo-01` и `find_duplicates`: один Job, первый создавший запрос получает 202, повтор — 200 с тем же ID. Конкурентная гонка решается уникальностью ключа в БД. Если клиент прислал разные ключи, это два намеренных запуска. | [Создание и повтор](api/README.md#создание-и-повтор), [OpenAPI](api/openapi.yaml), `POST /jobs`, ответы 202/200; [ADR-0002](adr/0002-idempotency.md#решение) |
| К2 Ответ потерялся | После таймаута клиент повторяет исходное тело и прежний ключ. Если фиксация была успешной, получает 200 с прежним ID; если откатилась — после восстановления 202 с одним новым Job. Уже существующее задание не запускается повторно. При недоступной БД — 503 `storage_unavailable`. | [Создание и повтор](api/README.md#создание-и-повтор), OpenAPI `POST /jobs`, 200/202/503; [ADR-0002](adr/0002-idempotency.md#решение) |
| К3 Неизвестная операция | Новый ключ и `operation: "remove_photos"`: 422 `unknown_operation`, `details.field = "body.operation"`, Job не создан. Для уже занятого ключа с другой парой параметров раньше срабатывает 409 `idempotency_conflict`. | [Порядок проверок](api/README.md#создание-и-повтор), OpenAPI `POST /jobs`, 422/409 и схема `Operation` |
| К4 Кривые параметры | Отсутствует `dataset_id`, пришло число вместо строки или лишнее поле: 422 `invalid_request` с перечнем полей. Синтаксически невалидный JSON или повтор имён полей — 400 `invalid_json`. Job не создаётся. | [Создание и повтор](api/README.md#создание-и-повтор), OpenAPI `CreateJob`, `Error`, `ErrorDetail`, ответы 400/422 |
| К5 Воскрешение | Повтор создания с прежним ключом для `done`, `failed` или `cancelled` возвращает 200 с прежним Job. Новый ключ создаёт новый Job. Запрос к `/restart` возвращает 404 `route_not_found`. Прямая смена конечного состояния отклоняется с `invalid_transition`. | [Состояния Job](architecture.md#состояния-job), [Чтение результата](api/README.md#чтение-результата), [ADR-0002](adr/0002-idempotency.md#решение) |
| К6 Отмена | `POST /jobs/{id}/cancel` переводит `created` в `cancelled` и возвращает 200. Повтор возвращает то же состояние и время отмены. Если Runner зафиксировал старт первым, запрос получает 409 `job_not_cancellable`, анализ продолжается, а отчёт доступен после `done`. | [Отмена Job](api/README.md#отмена-job), [ADR-0004](adr/0004-cancel-created.md#решение), OpenAPI `POST /jobs/{id}/cancel` |
| К7 Огромный вход | Тело POST >8192 байт → 413 без Job. Ошибочно большой каталог → 503 `catalog_unavailable` до создания. Внешний файл >5 МиБ или >12 млн пикселей → уже созданный Job получает `failed/image_too_large`; состояние читается с 200, отчёт — 409 `job_failed`. Новая работа сверх 20 незавершённых Job → 503 `service_busy`. | [Лимиты](api/README.md#лимиты-и-внешняя-зависимость), OpenAPI `x-limits`, 413/503, `JobFailure`; [ADR-0001](adr/0001-single-process.md#решение) |
| К8 Чужой или несуществующий id | Некорректный UUID даёт 422, а корректный UUID, которого нет в БД, даёт 404 `job_not_found`. В общем демо любой клиент с известным ID может прочитать Job и отменить его в `created`. | [Чтение результата](api/README.md#чтение-результата), [Отмена Job](api/README.md#отмена-job), [ADR-0003](adr/0003-demo-boundaries.md#решение) |
| К9 Перезапуск сервера | Перед приёмом запросов старые `running` становятся `failed` с `execution_interrupted`. Задания в `created` остаются в очереди, конечные состояния сохраняются. Для повторного анализа клиент создаёт новый Job с новым ключом. | [Перезапуск](architecture.md#перезапуск-и-ошибки-хранения), [ADR-0001](adr/0001-single-process.md#решение), OpenAPI `JobFailure` и описание `GET /jobs/{id}` |
| К10 Внешний сервис | Молчание источника → общий срок 10 с на попытку, максимум три попытки, затем `failed/source_timeout`. Мусор вместо JPEG → `failed/invalid_image` без повтора; недопустимый redirect → `source_invalid_response`. Полей JSON у бинарного ответа Picsum нет; смена формата/статуса рассматривается как нарушение контракта источника. HTTP-чтение состояния → 200 с причиной, отчёта → 409 `job_failed`. | [Лимиты и внешний источник](api/README.md#лимиты-и-внешняя-зависимость), [Ошибки обработки](api/README.md#ошибки-обработки), OpenAPI `JobFailure` и `GET /jobs/{id}/result` |

Для всех десяти карт определены ответы API. По К6 можно отменить ожидающий Job. Уже начатый анализ выполняется до завершения. По К8 доступ определяется известным ID в общем учебном экземпляре.

## Что предложил ИИ

ИИ использован для подготовки документов и проверки согласованности. В качестве исходного материала использованы требования p1, проектные схемы HTTP/Tool и колода. Следующий промпт задаёт выполненный в этом чате разбор атак; отдельный запуск другой модели не заявляется:

> Проверь контракт сервиса meandme как атакующий. API создаёт AnalysisJob по dataset_id и operation с Idempotency-Key, возвращает состояние и сохранённый результат. Два Tool ищут точные копии по SHA-256 и оценивают яркость/резкость. Источник — Picsum; лимиты p1: 1–10 файлов, 5 МиБ на файл, таймаут 10 секунд и два повтора. Учти приложенные контракты HTTP и Tool и карты К1–К10. Найди ещё три конкретные ситуации, где правила неоднозначны или недостаточны. Для каждой укажи вход, риск, точный ответ или изменение контракта. Не добавляй аккаунты, обучение моделей и мобильное приложение.

| Находка | Решение и изменение | Обоснование |
|---|---|---|
| Ответ создания потерялся; до повтора тот же `dataset_id` удалён или изменён в каталоге. Если сначала проверять текущий каталог, повтор получит ошибку или новый состав. | Принято: после структурной проверки сначала искать ключ и сравнивать исходную пару параметров. Для существующего ключа возвращать сохранённый Job со снимком состава и `catalog_version`. [ADR-0002](adr/0002-idempotency.md#решение), [порядок создания](api/README.md#создание-и-повтор). | Повтор должен узнавать судьбу прежнего запроса, а не зависеть от текущего состояния каталога. Новый ключ использует новый каталог. |
| PNG меньше 5 МиБ содержит огромное число пикселей и требует много памяти при декодировании. | Принято: лимит 12 000 000 пикселей, проверка размеров до полного декодирования, ошибка `image_too_large`; анализ по одному изображению. [Лимиты](api/README.md#лимиты-и-внешняя-зависимость), [контракт Tool](tool-contract.md#вход), OpenAPI `x-limits`. | Ограничение сетевых байтов не ограничивает размер распакованного изображения. |
| Источник посылает по байту каждые девять секунд: таймаут ожидания отдельного чтения не срабатывает, Job занимает Runner слишком долго. | Принято: 10 секунд на всю попытку, включая redirects и чтение потока; общий срок не сбрасывается при получении байта. После двух повторов — `source_timeout`. [Правила источника](api/README.md#лимиты-и-внешняя-зависимость). | Ограниченное число повторов полезно только при ограниченной длительности каждой попытки. |

Отдельные изменения, якобы внесённые во время пары, не приписываются этой версии. Документы подготовлены 10 ноября на основе p1 и колоды; личное участие в занятии учитывается отдельно в отчёте p2.

## Что проверено локально

Структура OpenAPI, разрешение `$ref`, JSON-примеры и отрицательные примеры проверяются скриптом `tools/check_contract.py`. Mermaid-диаграммы проверяются парсером при подготовке. Полный протокол проверки находится в локальном `practice-2/review-checklist.md` и не является отчётом об испытаниях сервиса. Сценарии сети, БД, гонки и перезапуска проверяются на реализации в следующих практиках.
