# Правила HTTP API

Машиночитаемый контракт — [openapi.yaml](openapi.yaml), OpenAPI 3.1.0. Он описывает целевой API; работающий сервер в практику 2 не входит. Здесь уточняются порядок проверок и правила, которые нельзя полностью выразить одной JSON Schema.

## Операции

| Запрос | Успех | Отказ |
|---|---|---|
| `POST /jobs` | 202 — создан, 200 — повтор прежнего ключа | 400, 409, 413, 415, 422, 500, 503 |
| `GET /jobs/{id}` | 200 — состояние и ошибка Job, если есть | 404, 422, 500, 503 |
| `GET /jobs/{id}/result` | 200 — сохранённый полный отчёт | 404, 409, 422, 500, 503 |
| `POST /jobs/{id}/cancel` | 200 — Job отменён или уже был отменён | 404, 409, 422, 500, 503 |
| `GET /health` | 200 — БД и обработчик готовы | 500, 503 |

Все ответы приложения — JSON. Ошибка имеет форму `{code, message, details, correlation_id}`. `details` всегда массив объектов `{field, reason}`; неверное поле указано как `body.operation`, `header.Idempotency-Key` или `path.id`. Для общей ошибки массив пуст. Всякий HTTP-ответ получает `X-Correlation-ID` — новый UUID обращения; в теле ошибки он совпадает с `correlation_id`. Сохранённый Job содержит ID обращения, которым был создан: при повторном чтении это другой ID, и он не переписывается.

Неизвестный путь возвращает 404 `route_not_found`. Неподдерживаемый метод известного пути возвращает 405 `method_not_allowed` с `Allow`. Для `/jobs/{id}` разрешён GET, для `/jobs` и `/jobs/{id}/cancel` разрешён POST. Эти общие ответы заданы в `x-routing-errors` OpenAPI. Ошибки маршрутизации и валидации FastAPI приводятся к единому формату.

## Создание и повтор

Тело — ровно два обязательных строковых поля: `dataset_id` и `operation`. Лишние поля запрещены. Пример: `{"dataset_id":"demo-01","operation":"find_duplicates"}`. `Idempotency-Key` обязателен: от 1 до 128 символов `[A-Za-z0-9_-]`, регистр значим; повторяющиеся одноимённые заголовки отклоняются как `invalid_request`.

Порядок проверок определяет ответ, если ошибок несколько:

1. Тело ограничивается 8192 байтами при чтении, независимо от `Content-Length`. Превышение — 413 `request_too_large`.
2. Требуется `Content-Type: application/json` (параметр `charset=utf-8` допустим) и отсутствие сжатия тела. Иной media type или `Content-Encoding`, кроме `identity`, — 415 `unsupported_media_type`.
3. Невалидный JSON и повторяющиеся имена полей JSON — 400 `invalid_json`. Валидный JSON неподходящей структуры, отсутствующие поля/ключ, неверный тип, пустая строка или лишние поля — 422 `invalid_request` с перечислением нарушений.
4. Для существующего ключа сравнивается пара `(dataset_id, operation)` до проверки существования текущего набора. Совпадение — 200 с тем же Job; отличие — 409 `idempotency_conflict`. В сравнении участвуют точные строки; порядок полей JSON неважен. Ошибки шагов 1–3 также не обходятся повтором ключа.
5. Для нового ключа неизвестная строковая операция — 422 `unknown_operation`, неизвестный набор — 422 `unknown_dataset`. Некорректная конфигурация существующего набора — 503 `catalog_unavailable`. При двадцати незавершённых Job — 503 `service_busy`.
6. Job, ключ и снимок набора сохраняются вместе. 202 возвращает снимок `created`; `Location` указывает `/jobs/{id}`. Гонка одинаковых ключей разрешается ограничением уникальности БД: один новый Job, проигравший запрос читает его и отвечает 200 или 409.

JSON Schema задаёт допустимые операции перечислением, но выбор кода `unknown_operation` выполняется явно по шагу 5; его нельзя заменять общим `invalid_request` валидатора. Ошибка БД на любом шаге доступа к ней даёт 503 `storage_unavailable`, без обещания, что транзакция точно откатилась. После потерянного ответа или такого 503 клиент повторяет прежний запрос с прежним ключом. Новые ключи означают новые анализы, даже для одинаковых параметров. См. [ADR-0002](../adr/0002-idempotency.md).

## Чтение результата

`id` — UUID. Неверный формат даёт 422 `invalid_request`, правильный, но отсутствующий ID — 404 `job_not_found`. Авторизации нет: Job по известному ID доступен любому клиенту учебного экземпляра. Личные данные запрещены границами проекта, а не защищены случайностью UUID.

Для `created` и `running` запрос отчёта возвращает 409 `result_not_ready`, для `failed` — 409 `job_failed`, для `cancelled` — 409 `job_cancelled`. При `job_failed` в `details` указан `job.error.code`. Сохранённую причину сбоя клиент получает через `GET /jobs/{id}`, который возвращает 200 для любого существующего Job. Для `done` чтение отчёта возвращает 200 без повторной загрузки и анализа. В JSON результата операция и `data` всегда соответствуют друг другу. Все даты — UTC ISO 8601.

`done`, `failed` и `cancelled` — конечные состояния. Попытка доменного перехода из них даёт `invalid_transition`. Повтор запроса создания с прежним ключом возвращает существующий Job, в том числе отменённый. Для нового запуска нужен новый ключ.

## Отмена Job

`POST /jobs/{id}/cancel` вызывается без тела и без `Idempotency-Key`. В учебном экземпляре отмена доступна любому клиенту, знающему ID. [Границы демо](../adr/0003-demo-boundaries.md)

| Состояние в момент отмены | Ответ и эффект |
|---|---|
| `created` | 200 с Job в состоянии `cancelled`. Фиксируется `finished_at`, поля `started_at` и `error` равны `null`. Место в очереди освобождается |
| `cancelled` | 200 с сохранённым Job и прежним `finished_at` |
| `running`, `done`, `failed` | 409 `job_not_cancellable`. В `details` указывается `job.state` и его текущее значение |
| Неверный или отсутствующий ID | 422 `invalid_request` для некорректного UUID, 404 `job_not_found` для корректного UUID, которого нет в БД |

Отмена и захват Runner конкурируют за один атомарный переход из `created`. Если отмена зафиксирована первой, Runner пропускает Job. Если старт зафиксирован первым, API отклоняет отмену и возвращает актуальное состояние. При недоступной БД API возвращает 503 `storage_unavailable`. Если клиент потерял ответ, он может повторить отмену и прочитать сохранённый Job. [ADR-0004](../adr/0004-cancel-created.md)

## Лимиты и внешняя зависимость

| Ресурс | Ограничение | Где проявляется отказ |
|---|---|---|
| JSON создания | 8192 байта | 413 `request_too_large`, Job не создаётся |
| `dataset_id` | 1–64 символа `[A-Za-z0-9_-]` | 422 `invalid_request` |
| `operation` | Непустая строка до 64 символов; две известные операции | Неверная форма — 422 `invalid_request`, неизвестное имя — 422 `unknown_operation` |
| Каталог | 1–10 элементов, уникальные ID; копия ссылается только на предыдущий исходный элемент | 503 `catalog_unavailable` до создания нового Job |
| Очередь | Не более 20 записей в `created`/`running` | 503 `service_busy` для нового ключа |
| Файл | До 5 × 1024 × 1024 байт; только одно кадровое изображение JPEG/PNG | Ошибка обработки `image_too_large` / `unsupported_image_format` |
| Разрешение | Обе стороны от 3 пикселей, ширина × высота ≤ 12 000 000 | `invalid_image` при слишком малом, `image_too_large` при слишком большом |
| Сетевая попытка | Общий срок 10 секунд, включая перенаправления и всё чтение потока | `source_timeout` после исчерпания попыток |
| Перенаправления | До трёх за попытку; только HTTPS и узлы `picsum.photos`, `fastly.picsum.photos` | `source_invalid_response` без повтора |
| Повторы | До двух дополнительных попыток при сетевой ошибке, timeout, 429 или 5xx; паузы 0,5 и 1 с | Ошибка источника после третьей неудачи |

Проверяются статус, Content-Type (`image/jpeg` или `image/png`), фактический формат и декодирование. `Content-Length` не считается достоверным ограничением: поток прекращается при превышении 5 МиБ. Проверка количества пикселей выполняется до полного декодирования; предупреждение Pillow о decompression bomb трактуется как отказ, а не отключается. Анимированный PNG и GIF не поддерживаются. Лимит памяти всего набора дополнительно ограничен десятью файлами по 5 МиБ; декодирование и расчёт выполняются по одному изображению.

Отсутствующий/неизображающий Content-Type, HTML вместо картинки или повреждённый JPEG дают `invalid_image`. Валидный, но неподдерживаемый формат даёт `unsupported_image_format`. HTTP 404 даёт `source_not_found`; прочие 4xx, кроме 429, — `source_rejected`, без повтора. Для чередующихся временных отказов сохраняется код последней попытки: `source_timeout` для таймаута, `source_unavailable` для сети/429/5xx. `Retry-After` источника не продлевает выбранные фиксированные паузы учебной версии.

При запретном redirect запрос по новому адресу не выполняется. Каталог тестового профиля подключает отдельный fake-сервис через тестовый адаптер; ограничения production-адаптера не отключаются. Десять секунд — лимит одной попытки загрузки одного файла, а не всего Job. Ожидание очереди не имеет обещанного SLA.

## Ошибки обработки

Эти коды сохраняются в `Job.error` и наблюдаются в HTTP 200 ответа состояния, а не как новый синхронный HTTP-отказ прежнего POST:

| Код | Причина |
|---|---|
| `source_timeout` | Истёк общий срок последней попытки |
| `source_unavailable` | Сеть, HTTP 429 или 5xx после повторов |
| `source_not_found` | Источник ответил 404 |
| `source_rejected` | Прочий неповторяемый 4xx |
| `source_invalid_response` | Недопустимое перенаправление или неожиданный HTTP-статус |
| `invalid_image` | Неизображающий ответ, ошибка декодирования или слишком малое разрешение |
| `unsupported_image_format` | Формат вне JPEG/PNG или несколько кадров |
| `image_too_large` | Превышены байты или число пикселей |
| `invalid_tool_input` | Нарушены структурные предусловия Tool |
| `unknown_operation` | Сохранённая операция отсутствует в Registry при выполнении |
| `execution_interrupted` | Во время прошлого запуска процесс остановился в состоянии `running` |
| `internal_error` | Непредвиденная ошибка обработки без раскрытия внутренних данных |

Сбой любого обязательного элемента переводит весь Job в `failed`; частичных успешных отчётов нет. В `details.field` указывается `images.<image_id>.content` либо конкретное поле; для ошибки всего процесса — пустой массив. Номер Job и `correlation_id` позволяют найти подробности в логах. Перезапуск описан в [архитектуре](../architecture.md#перезапуск-и-ошибки-хранения).

## Примеры и проверка

В OpenAPI есть примеры создания, повторного ответа, обоих отчётов и всех HTTP-кодов ошибок. Условные UUID, метрики и хеши иллюстрируют формат; это не результаты запущенного сервиса. Межполевая согласованность (число изображений, уникальность членства в группах, соответствие предупреждений порогам) проверяется будущими тестами реализации, а не только JSON Schema.

Описание версии формата: [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0.html). Проверка структуры контракта: [openapi-spec-validator](https://openapi-spec-validator.readthedocs.io/en/latest/python.html).
