# Требования к сервису анализа фотогалереи

Практики 1–2, команда meandme. Здесь зафиксированы принятые решения; сценарии S1–S6 задают критерии приёмки для задач и тестов.

## Назначение и участник

Сервис анализирует небольшие демонстрационные наборы фотографий: находит точные дубликаты и выдаёт предупреждения о возможном размытии и недостаточной освещённости.

Участник всех сценариев — пользователь учебного сервиса, обращающийся к HTTP API через клиент. Первая версия не включает учётные записи и личные фотографии. Наборы определяет каталог приложения; источник изображений — Lorem Picsum или его тестовая замена.

## Термины и общие правила

- **Набор** — упорядоченный список из 1–10 элементов с уникальными идентификаторами. Элемент задаёт внешний файл или копию ранее загруженного элемента.
- **AnalysisJob** — один запуск одной операции над выбранным набором. Идентификатор набора, его состав и параметры операции фиксируются при создании Job; изменение каталога не меняет уже созданное задание. Байты живого внешнего источника между разными Job могут отличаться.
- **Точный дубликат** — файл с теми же байтами, определяемый по совпадению SHA-256. Визуальное сходство, перекодирование и совпадение изображения при разных метаданных не входят в это определение.
- **Предупреждение о качестве** — результат фиксированной эвристики, а не оценка художественной ценности или основание для автоматического удаления.
- **Tool** — исполнитель операции с общим контрактом `execute(input) → ToolResult`. `Registry` выбирает исполнителя по имени; `Dispatcher` запускает его без зависимости от конкретного класса.

Поддерживаются операции `find_duplicates` и `assess_quality`. Каждый файл должен быть декодируемым JPEG или PNG; разрешение — не менее 3×3 пикселей для расчёта показателя резкости. Внешние демонстрационные изображения имеют размер 800×600. Сервис читает исходные байты и не изменяет оригиналы. Для сравнения результатов список идентификаторов внутри группы дубликатов и список самих групп упорядочиваются по идентификаторам; одиночные файлы в группы не включаются.

Входные параметры проверяются до создания Job. Неизвестная операция, неизвестный набор, пустой ключ идемпотентности и неверная структура запроса отклоняются без создания Job. Ошибка загрузки или декодирования после начала обработки переводит Job в `failed`. Частичный успешный отчёт не публикуется.

## Правила оценки качества

Применяются следующие эвристики. Их проверка выполняется на фиксированных изображениях; универсальная точность оценки качества не заявляется.

1. Изображение переводится в RGB; для PNG с прозрачностью перед анализом используется белый фон. Серый уровень `Y` рассчитывается в диапазоне 0–255: `0.299R + 0.587G + 0.114B`.
2. Яркость — среднее `Y` по изображению. При значении меньше 40 добавляется предупреждение `low_brightness`.
3. Резкость — дисперсия отклика дискретного оператора Лапласа: `L = Y_слева + Y_справа + Y_сверху + Y_снизу − 4Y`. Используются внутренние пиксели без внешней рамки; перед вычислением изображение не масштабируется. При дисперсии меньше 100 добавляется предупреждение `possible_blur`.
4. Значение, равное порогу, предупреждение не вызывает. В отчёте сохраняются показатели, применённые пороги, коды предупреждений и понятные причины. Для сравнений применяются неокруглённые показатели; округление допустимо только при отображении.

Пороги 40 и 100 — стартовые параметры учебной версии. Их изменение требует обновления требований и регрессионных тестов. Тесты используют известные значения или явно заданный допуск, а не ожидание «на этом фото красиво». Изображение без деталей также может получить `possible_blur`; это известное ограничение эвристики.

## S1. Найти точные дубликаты

**Участник:** пользователь сервиса. **Цель:** увидеть группы одинаковых файлов в наборе.

**Основной поток:**

1. Пользователь выбирает набор и операцию `find_duplicates`.
2. Отправляет `POST /jobs` с параметрами и новым ключом идемпотентности.
3. Сервис создаёт Job, возвращает его ID и принимает работу к выполнению.
4. При обработке сервис загружает и проверяет изображения, создаёт предусмотренные каталогом копии байтов и запускает `DuplicateFinder`.
5. Результат сохраняется; Job становится `done`.
6. Пользователь получает отчёт по ID Job.

**Критерии приёмки:**

- **Дано:** набор содержит файл A, его точную копию B и отличный файл C. **Когда:** анализ завершён. **Тогда:** Job имеет состояние `done`; отчёт содержит одну группу с A и B, без C.
- **Дано:** в наборе нет одинаковых файлов. **Когда:** анализ завершён. **Тогда:** возвращается пустой список групп и состояние `done`.
- **Дано:** анализ завершён. **Когда:** сравниваются исходные байты файлов до и после анализа. **Тогда:** они не изменены.

## S2. Оценить техническое качество

**Участник:** пользователь сервиса. **Цель:** получить измеримые показатели и причины предупреждений для каждого изображения.

**Основной поток:**

1. Пользователь отправляет запрос с операцией `assess_quality` и ID набора.
2. Сервис создаёт Job и получает изображения.
3. `QualityAnalyzer` рассчитывает показатели по правилам документа.
4. Сервис сохраняет отдельный результат для каждого элемента набора и завершает Job.
5. Пользователь читает отчёт.

**Критерии приёмки:**

- **Дано:** тестовая фикстура имеет среднюю яркость ниже 40. **Когда:** выполняется оценка. **Тогда:** её результат содержит `low_brightness`, рассчитанную яркость и порог 40.
- **Дано:** рассчитанная дисперсия Лапласа ниже 100. **Когда:** выполняется оценка. **Тогда:** результат содержит `possible_blur`, показатель и порог 100.
- **Дано:** показатель равен своему порогу. **Когда:** определяется соответствующее предупреждение. **Тогда:** оно не добавляется.
- **Дано:** анализ завершён. **Когда:** пользователь получает отчёт. **Тогда:** все элементы набора представлены по одному разу; найденные предупреждения не переводят Job в `failed`.

## S3. Получить состояние задания и отчёт

**Участник:** пользователь сервиса. **Цель:** узнать, выполняется ли анализ, и получить итог или причину ошибки.

**Основной поток:**

1. Пользователь сохраняет ID из ответа создания Job.
2. Запрашивает `GET /jobs/{id}`.
3. Сервис возвращает ID, операцию, набор, состояние и ошибку, если она есть.
4. После `done` пользователь запрашивает `GET /jobs/{id}/result`.
5. Сервис возвращает сохранённый отчёт, не запуская анализ повторно.

**Критерии приёмки:**

- **Дано:** Job существует. **Когда:** запрошено его состояние. **Тогда:** возвращается HTTP 200 с одним из состояний жизненного цикла.
- **Дано:** Job в `created` или `running`. **Когда:** запрошен отчёт. **Тогда:** возвращается HTTP 409 с кодом `result_not_ready`; анализ продолжается.
- **Дано:** Job в `done`. **Когда:** отчёт запрашивается повторно. **Тогда:** возвращается HTTP 200 с тем же сохранённым результатом без нового обращения к источнику.
- **Дано:** Job в `failed`. **Когда:** запрошено состояние. **Тогда:** HTTP 200 содержит код и причину сбоя; запрос отчёта возвращает HTTP 409 с `job_failed`, без частичного отчёта.
- **Дано:** Job в `cancelled`. **Когда:** запрошено состояние или отчёт. **Тогда:** состояние возвращается с HTTP 200, а запрос отчёта возвращает HTTP 409 с `job_cancelled`.
- **Дано:** Job с указанным ID отсутствует. **Когда:** запрошены его состояние или отчёт. **Тогда:** возвращается HTTP 404 с кодом `job_not_found`.

## S4. Повторить создание без дублирования работы

**Участник:** пользователь сервиса. **Цель:** безопасно повторить запрос, если ответ на первый запрос потерян.

**Основной поток:**

1. Пользователь создаёт Job с заголовком `Idempotency-Key`.
2. Повторяет запрос с тем же ключом и теми же параметрами.
3. Сервис находит ранее созданный Job и возвращает его ID и текущее состояние.
4. Новая работа не создаётся и не запускается.

**Критерии приёмки:**

- **Дано:** ключ K ещё не использовался. **Когда:** принят корректный запрос. **Тогда:** создаётся один Job, возвращается HTTP 202 и его ID.
- **Дано:** ключ K уже связан с Job. **Когда:** приходит тот же запрос, включая конкурентный повтор. **Тогда:** возвращается HTTP 200 с тем же ID; в БД существует ровно один Job для K.
- **Дано:** ключ K уже связан с Job. **Когда:** с K приходит другая операция или другой ID набора. **Тогда:** HTTP 409 содержит `idempotency_conflict`; существующий Job не изменяется.
- **Дано:** запрос не содержит непустого ключа. **Когда:** выполняется создание. **Тогда:** HTTP 422 содержит `invalid_request`; Job не создаётся.

В первой версии ключи общие для учебного экземпляра и сохраняются вместе с Job бессрочно. Порядок полей JSON не влияет на сравнение параметров. Повтор для `done`, `failed` или `cancelled` возвращает прежний Job. Для нового запуска нужен новый ключ.

## S5. Обработать повреждённое изображение

**Участник:** пользователь сервиса. **Цель:** получить понятную причину невозможности анализа вместо ложного успешного результата.

**Поток ошибки:**

1. В тестовом каталоге выбран набор с повреждённым изображением или неподдерживаемым форматом.
2. Корректный запрос создаёт Job; начинается загрузка.
3. HTTP-запрос возвращает данные, но проверка формата или декодирование завершается ошибкой.
4. Job переходит из `running` в `failed`; сохраняется причина и ID проблемного элемента.
5. Пользователь получает ошибку через сведения о Job.

**Критерии приёмки:**

- **Дано:** источник возвращает повреждённый JPEG или HTML вместо изображения. **Когда:** данные проверяются. **Тогда:** Job становится `failed` с `invalid_image`; результат `done` не публикуется.
- **Дано:** файл имеет неподдерживаемый формат, например GIF. **Когда:** определяется формат. **Тогда:** Job становится `failed` с `unsupported_image_format`.
- **Дано:** один элемент набора повреждён, остальные корректны. **Когда:** обнаружена ошибка. **Тогда:** весь Job становится `failed`; частичный отчёт не выдаётся, повреждённый ответ не запрашивается повторно автоматически.
- **Дано:** один Job завершился ошибкой изображения. **Когда:** создаётся другой Job с корректной фикстурой. **Тогда:** сервис принимает и выполняет его штатно.

Наборы с ошибками доступны в тестовой конфигурации; они не подменяют обычный `demo-01`.

## S6. Обработать отказ внешнего источника

**Участник:** пользователь сервиса. **Цель:** получить завершённое ошибкой задание при недоступном источнике и успешный результат при кратком восстанавливаемом сбое.

**Поток ошибки:**

1. Пользователь запускает Job с корректными параметрами.
2. Адаптер обращается к источнику изображений.
3. Происходит сетевой сбой, timeout либо временный HTTP-отказ.
4. Адаптер выполняет ограниченные повторы.
5. Если данные так и не получены, Job становится `failed` с причиной; бесконечное ожидание не допускается.

**Критерии приёмки:**

- **Дано:** fake-источник всегда отвечает HTTP 503. **Когда:** выполняется загрузка одного файла. **Тогда:** выполняется не более трёх попыток — исходная и два повтора; после исчерпания попыток Job получает `failed` с `source_unavailable`.
- **Дано:** fake-источник превышает настроенный таймаут во всех попытках. **Когда:** ожидание каждой попытки прерывается адаптером. **Тогда:** после не более трёх попыток Job становится `failed` с `source_timeout`.
- **Дано:** первая попытка загрузки возвращает 503, вторая — корректный JPEG; остальные файлы набора корректны и обработка проходит без других сбоев. **Когда:** выполняется повтор и анализ завершается. **Тогда:** Job становится `done`; третья попытка загрузки этого файла не выполняется.
- **Дано:** источник возвращает HTTP 404. **Когда:** получен ответ. **Тогда:** повторов нет; Job становится `failed` с `source_not_found`.

## Жизненный цикл Job

| Состояние | Значение | Допустимый следующий шаг |
|---|---|---|
| `created` | Параметры проверены, Job сохранён, обработка ещё не началась | `running` или `cancelled` |
| `running` | Получение и проверка изображений, выполнение выбранной операции | `done` или `failed` |
| `done` | Полный отчёт сохранён | Нет, состояние конечное |
| `failed` | Сохранён код и причина ошибки, успешного отчёта нет | Нет, состояние конечное |
| `cancelled` | Задание отменено до загрузки изображений. Сохранено время отмены | Нет, состояние конечное |

Переходы, отсутствующие в таблице, отклоняются с `invalid_transition` без изменения Job. При запуске до приёма HTTP-запросов старые `running` переходят в `failed` с `execution_interrupted`. Сохранённые `created` остаются в очереди, конечные состояния сохраняются. Для повторного анализа нужен новый Job и новый ключ. [ADR-0001](adr/0001-single-process.md)

Начало обработки фиксируется до сетевой загрузки. Запись результата и переход в `done` выполняются в одной транзакции; запись ошибки и переход в `failed` — также в одной транзакции. Job не должен наблюдаться как `done` без сохранённого полного отчёта.

В практике 2 добавлена отмена ожидающего Job. Критерии приёмки приведены ниже. [ADR-0004](adr/0004-cancel-created.md)

- Если Job в `created`, `POST /jobs/{id}/cancel` возвращает HTTP 200 с `cancelled`. Место в очереди освобождается. Runner пропускает задание, поэтому загрузки и анализа не происходит.
- Если Job уже в `cancelled`, повтор отмены возвращает HTTP 200 с тем же временем отмены. Запись и ключ создания сохраняются.
- Если Job в `running`, `done` или `failed`, отмена возвращает HTTP 409 с `job_not_cancellable`. Состояние задания не меняется.
- Если отмена и Runner одновременно пытаются поменять `created`, фиксируется только один переход. После успешной отмены Runner пропускает Job, а после успешного старта запрос отмены получает HTTP 409.

## Источник и лимиты

[Lorem Picsum](https://picsum.photos/) подключается через адаптер `PicsumImageSource`. Примеры: `https://picsum.photos/id/10/800/600.jpg` и `https://picsum.photos/id/29/800/600.jpg`. Адаптер обрабатывает до трёх перенаправлений, включая переход на CDN. Адреса задаются каталогом и конфигурацией источника.

`demo-01` содержит элементы `photo-10`, `photo-29` и `photo-10-copy`. Третий элемент получает копию уже загруженных байтов первого, без отдельного запроса. Входной API принимает `dataset_id`, а не URL или путь к произвольному файлу. Внешний источник используется при выполнении Job; автоматические тесты работают с fake-адаптером или отдельным HTTP fake-сервисом.

| Ограничение | Значение первой версии |
|---|---|
| Размер набора | От 1 до 10 элементов, включая копии |
| Размер файла | Не более 5 МиБ = 5 × 1024 × 1024 байт |
| Форматы | JPEG, PNG |
| Минимальное разрешение | 3×3 пикселя |
| Таймаут сетевого запроса | 10 секунд; это не обещание длительности всего Job |
| Повторы | Не более двух дополнительных попыток при сетевых сбоях, timeout, HTTP 429 или 5xx |
| Паузы перед повторами | 0,5 секунды перед первым повтором, 1 секунда перед вторым |

HTTP 4xx, кроме 429, неверный формат, повреждение и превышение размера не повторяются. Проверяются статус, тип ответа и фактический формат декодированного изображения. Размер ограничивается при чтении потока, даже если заголовок `Content-Length` отсутствует или неверен. Превышение размера даёт `image_too_large`, слишком маленькое разрешение — `invalid_image`. Некорректный каталог отклоняется до создания Job. Параметры HTTP fake-сервиса позволяют проверить эти случаи без обращения к Picsum.

## API, хранение и проверка по этапам

`POST /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/result`, `POST /jobs/{id}/cancel`. Все ответы ошибок используют поля `code`, `message`, `details`, `correlation_id`. Доменный `invalid_transition` отклоняет недопустимую смену состояния без изменения Job. HTTP 409 используется для конфликта ключа, недоступного отчёта и отмены уже начатого анализа.

Пример тела создания: `{"dataset_id": "demo-01", "operation": "find_duplicates"}`. Неизвестная операция даёт HTTP 422 с `unknown_operation`, неизвестный набор — HTTP 422 с `unknown_dataset`. Формальные схемы запросов и ответов, включая результаты двух Tool, зафиксированы в [OpenAPI](api/openapi.yaml) и [контракте Tool](tool-contract.md). Порядок проверок, единые HTTP-ошибки и расширенные лимиты — в [правилах API](api/README.md).

БД хранит Job, зафиксированный состав набора, параметры, ключ идемпотентности, результаты и ошибки. Ключ имеет ограничение уникальности. Бинарные оригиналы не хранятся в таблицах БД. На практике 4 используется SQLite; к практике 7 хранилище переводится на PostgreSQL отдельным сервисом с теми же миграциями Alembic.

Модульные тесты проверяют ядро, допустимые и запрещённые переходы, выбор Tool и результаты на фиксированных файлах. Интеграционные и контрактные тесты проверяют API, хранение, миграции, конкурентную идемпотентность, гонку отмены со стартом и сетевой адаптер. Команда тестов — `pytest`. CI запускает её без живого Picsum. Код ядра не зависит от HTTP-фреймворка, БД или сетевого клиента.

К практике 7 приложение пишет JSON-логи с `correlation_id` и `job_id`, читает конфигурацию из окружения и предоставляет `GET /health`: HTTP 200 при доступной БД и HTTP 503 при её недоступности, без раскрытия секретов. Запуск из чистого клона — `docker compose up --build`; миграции применяются при запуске.

## Что предложил ИИ

Использован следующий промпт:

> Мы проектируем сервис анализа тестовой фотогалереи. Он получает изображения из Lorem Picsum через HTTP-адаптер, ищет точные дубликаты по SHA-256 и оценивает техническое качество по фиксированным правилам. Уже учтены повреждённое изображение и недоступность источника. Предложи ещё три способа сломать основной сценарий; для каждого укажи входные условия и ожидаемое поведение. Не расширяй проект до мобильного приложения или обучения моделей.

| Предложение ИИ | Решение | Почему и где отражено |
|---|---|---|
| Два запроса одновременно используют один ключ идемпотентности; оба пытаются создать Job | Принято | Возможен повтор после потери ответа. Требуется один Job и одинаковый ID в обоих ответах. Закреплено в S4 и уникальности ключа в БД; проверяется интеграционным тестом. |
| Источник отдаёт слишком большой файл без `Content-Length` или с неверным значением заголовка | Принято | Проверки одного заголовка недостаточно. Чтение прекращается после лимита 5 МиБ, Job получает `failed` с `image_too_large`. Закреплено в лимитах источника; проверяется HTTP fake-сервисом. |
| Пользователь запрашивает отчёт до окончания обработки или после ошибки | Принято | Нельзя выдать пустой ответ за успешный результат. Для незавершённого Job возвращается `result_not_ready`, для неуспешного — `job_failed`. Закреплено в S3. |

## Уточнения практики 2

- Новая работа выполняется в фоне одним Runner в одном процессе; очередь хранится в БД. Не более 20 Job находятся в `created`/`running`, превышение для нового ключа — 503 `service_busy`.
- При повторе ключа сохранённый Job проверяется до текущего каталога. Снимок состава и версия каталога не меняются; новый ключ использует текущий каталог.
- Тело POST ограничено 8192 байтами. Декодируемое изображение содержит не более 12 000 000 пикселей и один кадр; превышение числа пикселей — `image_too_large`, анимация — `unsupported_image_format`.
- Десять секунд ограничивают всю сетевую попытку, включая перенаправления и чтение потока; получение отдельного байта не продлевает срок.
- После перезапуска начатые Job завершаются `execution_interrupted`, а ещё не начатые остаются в очереди; это уточняет первоначальное исключение обработки аварий.
- Полный контракт и пределы гарантии — в [архитектуре](architecture.md), [API](api/README.md) и [ADR](adr/0001-single-process.md). Эти уточнения относятся к проекту API, а не заявляют готовую реализацию.
