# meandme — сервис анализа фотогалереи

**Статус:** постановка задачи для практики 1. Технические решения приняты; реализация приложения, API, тестов и контейнерного запуска выполняется на следующих этапах.

## Проблема и пользователи

При разборе набора фотографий приходится вручную искать повторяющиеся файлы и просматривать технически неудачные кадры. Сервис выдаёт список точных дубликатов и предупреждения о возможном размытии или недостаточной освещённости.

Первая версия предназначена для анализа небольших демонстрационных наборов, заранее включённых в каталог приложения. Она не подключается к личной фотогалерее пользователя. Для демонстрации используются выбранные тестовые изображения без персональных данных.

## Что входит в систему

- Создание задания `AnalysisJob` для набора изображений и одной операции.
- Поиск точных дубликатов: файлов с одинаковыми байтами, определяемых по SHA-256.
- Оценка размытия и освещённости по фиксированным правилам.
- Получение состояния задания и отчёта с причинами предупреждений.
- Загрузка демонстрационных изображений из Lorem Picsum через сетевой адаптер.
- Сохранение заданий, результатов и ошибок в БД с миграциями.
- Идемпотентное создание задания: повтор запроса с тем же ключом и параметрами не создаёт новую работу.

## Что не входит в первую версию

- Удаление, перемещение или изменение оригиналов фотографий.
- Поиск визуально похожих, но побайтово разных изображений.
- Выбор субъективно «лучшего» кадра, персонализация и обучение моделей.
- Распознавание людей и обработка личных фотогалерей.
- Pinterest, Google Photos, iCloud и другие интеграции с пользовательскими аккаунтами.
- Мобильное приложение и сложный пользовательский интерфейс.
- Авторизация и многопользовательский режим: это учебный сервис с общим демонстрационным каталогом, а не готовый публичный продукт.

Предупреждение о качестве — результат эвристики, а не команда удалить изображение. Тёмный или намеренно размытый кадр может быть удачным; решение о сохранении остаётся за пользователем.

## Основной сценарий

1. Пользователь выбирает набор `demo-01` и операцию `find_duplicates` или `assess_quality`.
2. Клиент отправляет запрос создания Job с ключом идемпотентности.
3. Сервис возвращает идентификатор Job в состоянии `created`.
4. Исполнитель обработки переводит Job в `running`, получает изображения через адаптер и запускает выбранный анализатор.
5. Пользователь проверяет состояние по ID. При успехе Job становится `done`, при ошибке — `failed`.
6. Для `done` пользователь получает отчёт. Для `failed` — код и объяснение ошибки через сведения о Job.

Для запуска двух операций создаются два отдельных Job. В первой версии частичного успешного отчёта нет: если обязательный файл нельзя получить или декодировать, весь Job завершается ошибкой.

## Источник изображений и тестовые данные

[Lorem Picsum](https://picsum.photos/) отдаёт JPEG по фиксированному ID и размеру без регистрации и API-токена:

- [Фото с ID 10, 800×600](https://picsum.photos/id/10/800/600.jpg).
- [Фото с ID 29, 800×600](https://picsum.photos/id/29/800/600.jpg).
- [Размытая версия фото 10](https://picsum.photos/id/10/800/600.jpg?blur=5) — дополнительный пример для демонстрации.

Набор `demo-01` включает два первых изображения и отдельный элемент с копией байтов первого файла. Копия создаётся после однократной загрузки первого файла в рамках Job; повторный сетевой запрос для неё не нужен. Так в наборе есть гарантированный точный дубликат. Для обязательного демонстрационного набора не используется случайная выдача Picsum.

Фиксированный ID выбирает фотографию, но не гарантирует неизменность её байтов и не задаёт эталонную оценку качества. Поэтому автоматические тесты используют фиксированные локальные JPEG/PNG и fake-источник. Размытие, затемнение, копирование и повреждение тестовых файлов документируются вместе с их происхождением. PNG проверяется локальными фикстурами; основной внешний источник используется для JPEG.

Лимиты первой версии: 1–10 элементов набора, не более 5 МиБ на загружаемый файл, таймаут сетевого запроса 10 секунд и не больше двух повторов при временных сбоях. Пользователь передаёт ID набора из каталога, а не произвольный URL.

## Устройство сервиса

```text
HTTP-запрос → AnalysisJob → Dispatcher → Registry → Tool → ToolResult
```

`Registry` хранит соответствие имени операции исполнителю. `Dispatcher` получает исполнителя из реестра и не содержит ветвлений по конкретным классам анализаторов. Общий контракт — `Tool.execute(input) → ToolResult`.

| Операция | Исполнитель | Результат |
|---|---|---|
| `find_duplicates` | `DuplicateFinder` | Группы идентификаторов файлов с одинаковым SHA-256 |
| `assess_quality` | `QualityAnalyzer` | Показатели яркости и резкости, предупреждения и их причины |

Жизненный цикл: `created → running → done / failed`. Состояние `done` означает, что анализ выполнен, даже если найдены дубликаты или предупреждения о качестве. Недопустимые переходы отклоняются.

## Стек и API

Python 3.12, FastAPI, Pydantic, Pillow, NumPy, HTTPX, SQLAlchemy и Alembic. В прототипе используется SQLite; к практике 7 хранилище переводится на PostgreSQL отдельным сервисом. Тесты — pytest; CI — GitHub Actions; запуск — Docker Compose.

| Метод и путь | Назначение |
|---|---|
| `POST /jobs` | Создать Job с заголовком `Idempotency-Key` |
| `GET /jobs/{id}` | Получить состояние, параметры и ошибку Job |
| `GET /jobs/{id}/result` | Получить отчёт завершённого Job |
| `GET /health` | Проверить приложение и доступность БД |

Машиночитаемый OpenAPI-контракт оформляется на практике 2. Правила и критерии приёмки приведены в [требованиях](docs/requirements.md).

## Проверка и запуск по этапам курса

- Практика 1: README, требования, backlog в Issues, правила работы и заявка на тему.
- Практики 2–4: контракты, доменное ядро, API и хранение с миграциями.
- Практики 5–6: автоматические тесты, CI, сетевой адаптер и fake-сервис.
- К практике 7: логи с `correlation_id`/`job_id`, health check, конфигурация из окружения, PostgreSQL и запуск из чистого клона.

После реализации тесты запускаются командой `pytest`, приложение — `docker compose up --build`. Инструкция настройки окружения и демонстрации добавляется вместе с реализацией. CI работает с фиксированными файлами и fake-источником; живой Picsum используется для отдельной демонстрации интеграции.

## Развитие во втором семестре

LLM подключается перед созданием Job как интерпретатор запроса пользователя: «найди одинаковые фотографии в demo-01» преобразуется в операцию `find_duplicates` и ID набора. Параметры проходят обычную валидацию. LLM также объясняет отчёт по сохранённым результатам, без выполнения произвольного кода и удаления файлов.
